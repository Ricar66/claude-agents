# Security Sentinel — report template

This is the format Security Sentinel uses to answer. It has three purposes: the agent follows the same order in every audit, readers know where to find each piece of information, and two runs can be compared (stable IDs, a status per finding).

Rules that apply to the whole report:

- **No secrets, tokens, passwords, keys or personal data** appear in the text. Use `[REDACTED]` and give only the file, line and type.
- Internal addresses and names (IPs, hosts, accounts) appear only when needed to fix the issue, and the report then becomes **internal**.
- Anything not verified says "not verified". No CVSS or EPSS number, and no version, without a source.

## 1. Markdown template

Copy the structure below. Sections marked "(when applicable)" can be dropped in short modes; sections 1 and 9 are never dropped.

```markdown
# Security report — <project> — <mode> — <YYYY-MM-DD>

Classification: <Internal | Public>   ·   Generated by: security-sentinel   ·   Requested by: <person or role>

## 1. Scope and stack
- Project and version: <repository>, branch <name>, commit <short sha>
- Mode: <triage | diff-review | deep-audit | threat-model | network-review | ai-agent-review | supply-chain | incident-triage | remediation-plan | verify-fix | release-gate>
- Active testing authorized: <no | yes — scope, window, who authorized>
- Detected stack (by file, not by assumption): <languages, frameworks, database, infrastructure, CI>
- Organizational context loaded: <yes | no>
- Files and areas read: <list or count per folder>
- Not accessed and why: <environments, servers, secrets, folders out of scope>
- Limitations: <what lowers confidence in the conclusions>

## 2. Architecture and trust boundaries
<components, inputs and outputs, where authentication and authorization happen, sensitive data, external dependencies>
Possible attack chains (conditional): <e.g.: "if route X is exposed to the internet, SS-003 + SS-007 allow…">

## 3. Executive summary
- Overall risk: <reasoned sentence, without "secure" or "invulnerable">
- Main exposures: <3 to 5, with IDs>
- What was not inspected: <short list>
- Immediate priority: <action>

## 4. Findings
| ID | Title | Severity | Confidence | Layer | Location | Status |
|---|---|---|---|---|---|---|
| SS-001 | … | High | Confirmed | API | src/rotas/pedidos.ts:42 | open |

### SS-001 — <title>
- Severity / confidence: <High / Confirmed>

- Impact (C/I/A and business): <…>

- Regression test: <positive and negative case>
- Rollback and side effects: <…>
- Residual risk: <…>
- Suggested owner / status: <… / open>
```

## 2. Finding fields

| Field | Required | Values and rules |
|---|---|---|
| `id` | yes | `SS-` + 3 or more digits. Keeps the number between runs when the previous findings are provided |
| `title` | yes | Short, describes the defect, not the fix |
| `severity` | yes | `critical`, `high`, `medium`, `low`, `info` (impact if exploited) |
| `confidence` | yes | `confirmed`, `probable`, `hypothesis` (strength of the evidence; independent of severity) |
| `layer` | yes | `application`, `identity`, `api`, `data`, `network`, `infrastructure`, `supply_chain`, `ai`, `operations`, `iot`, `other` |
| `location` | yes | File and lines, or configuration resource. Never invented |
| `flow` | yes for confirmed and probable | source → validation → authorization → destination |
| `evidence` | yes | Sanitized. No secrets or personal data |
| `cwe`, `asvs` | no | Only with a clear mapping. ASVS cites the version (e.g. `5.0.0`) |
| `cve` | no | Each item with `id`, `kev` (true, false or null), `epss` (score, percentile and date) or null, `source` and `checked_at` |
| `cvss` | no | Only v4.0 with a full vector and justification; without a vector, null |
| `status` | yes | `open`, `fixed_verified`, `partially_mitigated`, `not_fixed`, `not_verified`, `false_positive`, `risk_accepted` |

## 3. JSON output

When the user asks for JSON, the report follows the schema below (`schema_version` `1.0`, JSON Schema draft-07, chosen because most validators accept it). **Field names and enumerated values stay in English** and are the same in the Portuguese and English versions of this package, so that any tool reads both; free text (title, evidence, recommendation) stays in the language of the report.

| In the Markdown report | In the JSON |
|---|---|
| Critical, High, Medium, Low, Info | `critical`, `high`, `medium`, `low`, `info` |
| Confirmed, Probable, Hypothesis | `confirmed`, `probable`, `hypothesis` |
| open, fixed and verified, partially mitigated, not fixed, not verified, false positive, risk accepted | `open`, `fixed_verified`, `partially_mitigated`, `not_fixed`, `not_verified`, `false_positive`, `risk_accepted` |
| immediate, before production, next cycle, continuous improvement | `immediate`, `before_production`, `next_cycle`, `continuous_improvement` |
| assessed, partial, not assessed, NOT APPLICABLE | `assessed`, `partial`, `not_assessed`, `not_applicable` |
| GO, GO WITH EXCEPTIONS, NOT RECOMMENDED, INCONCLUSIVE | `GO`, `GO_WITH_EXCEPTIONS`, `NOT_RECOMMENDED`, `INCONCLUSIVE` |
| effort S, M, L | `S`, `M`, `L` |

## 4. Validation

- The schema and the example above were checked with `ajv` 6 (draft-07) at the time of creation; see `SECURITY_SENTINEL_SETUP.md`, validation section.
- The agent does not validate its own JSON. If the report is consumed by another tool, validate it before importing.
- SARIF is not part of this format. When the team needs SARIF, it must come from a tool that generates and validates SARIF 2.1.0 (CodeQL, Semgrep and others), not from text written by the model.
